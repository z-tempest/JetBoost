# fleet.json

Generated by `src/scripts/prepare_fleet_data.py` from a raw CMAPSS test
file. Pretty-printed (not minified) so it's readable directly in an
editor -- open it, don't just eyeball the minified original.

One array of aircraft. Each aircraft:

| Field         | Meaning                                                              |
|---------------|-----------------------------------------------------------------------|
| `id`          | `unit-<engine id>` from the source CSV                                |
| `nickname`    | Display name                                                          |
| `history`     | One entry per logged cycle -- see below                               |
| `flightPath`  | Scene-space (x, y, z) points for the 3D map, one per history entry    |

There's deliberately no top-level "current" opSettings/PC1 snapshot --
the frontend derives "now" for each aircraft live from `history`, keyed
off wherever its marker currently is in its animated loop (see
`src/utils/liveCycle.ts`), so a popup, the sidebar breakdown, and the
fleet-wide chart can never each be looking at a different moment in its
timeline.

Each `history` entry:

| Field             | Meaning                                                          |
|-------------------|-------------------------------------------------------------------|
| `cycle`           | Cycle number                                                      |
| `opSettings`      | This cycle's altitude/Mach/TRA -- see the table below              |
| `sensors`         | This cycle's raw sensor readings, keyed by real short code (`T2`, `Nf`, `Ps30`, ...) |
| `pc1`             | First principal component of this cycle's z-scored sensor readings (not op settings). Fit once, via SVD, across every engine in the raw source file -- not just whichever units get sampled into this fleet.json -- so the component basis is stable regardless of fleet size. Sign is oriented to correlate positively with elapsed cycle, so higher PC1 = further degraded. See `fit_pca_pc1` in `prepare_fleet_data.py`. |
| `cyclesRemaining` | Cycles left before this test log was truncated. **Not a model prediction** -- it's a deterministic fact about the raw file (`total_cycles - cycle`). The model's actual predicted RUL is never in this file -- it comes from a live API call, see `src/hooks/usePredictions.ts`. |

Op setting / sensor labels and units are defined once, in
`src/data/sensorMeta.ts` -- that's the legend for every short code in
this file (`T2` = "Total temp, fan inlet", `Ps30` = "Static pressure,
HPC outlet", etc.), sourced from Table 2 of Saxena, Goebel, Simon &
Eklund (PHM08).

To regenerate from a fresh raw CSV:

```
python3 prepare_fleet_data.py <path-to-raw-test-file> fleet.json <num_units>
```

To make the visualized fleet the *same aircraft* your model is actually
scoring, point at your feature-engineered test set instead of sampling
independently:

```
python3 prepare_fleet_data.py <path-to-raw-test-file> fleet.json \
    --engine-ids-from <path-to-your-feature-engineered-test-set> \
    --engine-id-column <column holding the engine/unit id, e.g. Engine or unit_number>
```

To re-lay-out an existing fleet.json (e.g. after tuning the anchor
spread) without the original CSV: `python3 migrate_fleet_data.py
fleet.json fleet.json`. Note this carries over each entry's existing
`pc1` rather than recomputing it -- a real PCA fit needs the full raw
population, which migrate_fleet_data.py doesn't have access to.
